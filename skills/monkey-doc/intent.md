# 의도 확인

구조를 고르기 전에 다섯 칸을 정한다. 칸은 요청과 대화 맥락에서 먼저 읽는다.

| 칸 | 묻는 것 | 예 |
|---|---|---|
| 독자 | 누가 읽나, 이 주제를 얼마나 아나 | 다른 팀 개발자, 처음 접함 |
| 행동 | 읽고 나서 무엇을 하나 | 승인한다 / 따라 한다 / 값을 찾는다 / 이해한다 / 답한다 / 배운다 |
| 시간 | 얼마나 들여 읽나 | 30초 훑기 / 10분 정독 / 필요할 때 찾아봄 |
| 매체 | 어디서 읽나 | 메신저, PR, 위키, HTML, 채팅 |
| 수명 | 얼마나 오래 맞아야 하나 | 오늘만 / 이번 분기 / 결정 기록으로 계속 |

## 칸이 다 채워졌을 때

묻지 않는다. 고른 의도를 한 줄로 밝히고 쓴다.

<!-- monkey-lint: off -->
예: `의도: 고객 상담원 · 환불 문의를 순서대로 처리 · 문의가 올 때 찾아봄 · 사내 위키 · 환불 정책이 바뀔 때까지 → howto`
<!-- monkey-lint: on -->

## 칸이 비었을 때

구조를 가르는 칸이 비었을 때만 묻는다. 질문은 하나, 추천 답을 붙인다.

- 구조를 가르는 칸: **행동**(유형이 바뀐다), **매체**(메시지인지 문서인지, 그림 문법이 바뀐다), **시간**(맨 위 요약과 접기를 얼마나 쓸지 바뀐다).
- 구조를 덜 가르는 칸: 독자 수준(예시 위치만 바뀐다), 수명(코드 지도와 시간 표현만 바뀐다). 비면 기본값을 정하고 한 줄로 알린다.
- 기본값: 독자는 "같은 팀, 이 주제는 처음", 수명은 "몇 달", 매체는 "GitHub 마크다운".

<!-- monkey-lint: off -->
질문 예: "이 문서를 읽은 사람이 승인만 하면 되나요, 직접 적용까지 하나요? 승인만이라면 결정 요청으로 쓸게요(추천)."
<!-- monkey-lint: on -->

질문 하나로 정리되지 않으면 추천 답대로 쓰고 그렇게 정했다고 밝힌다. 답을 기다리느라 멈추지 않는 편이 낫다.

## 행동에서 유형으로

| 독자의 행동 | 기본 유형 |
|---|---|
| 선택지 중 하나를 승인하거나 고른다 | decision (결정 요청: 스펙·RFC) |
| 나중에 "왜 이렇게 했지?"를 확인한다 | adr |
| 무슨 일이 있었는지 알고 후속 조치를 정한다 | report (조사·장애 보고) |
| 시스템이 어떻게 움직이는지 이해한다 | explain (동작 설명) |
| 단계대로 따라 해서 작업을 끝낸다 | howto (How-to·런북) |
| 필요할 때 값 하나를 찾는다 | reference (레퍼런스) |
| 30초 안에 읽고 답하거나 한 가지를 한다 | message (메신저·메일) |
| diff를 보며 승인하고 나중에 변경 이유를 찾는다 | pr (PR 설명) |
| 시간을 들여 익히고 스스로 쓸 수 있게 된다 | study (학습 교보재) |

- 행동이 표의 두 줄에 반씩 걸리고 나누면 독자의 행동이 끊기면 맞는 유형이 없는 것이다. 새 구조를 조립한다.
- 행동이 표의 어느 줄과도 맞지 않아도 새 구조를 조립한다.
- 두 행동이 따로 일어나면(오늘 승인, 다음 주 적용) 나누는 편이 맞다. 문서 둘로 쓰고 서로 링크한다.
