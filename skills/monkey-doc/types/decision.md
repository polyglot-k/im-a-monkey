# 결정 요청 (decision)

- 언제: 독자가 읽고 선택지 중 하나를 승인하거나 고른다. 스펙, RFC, 설계 제안.
- 블록 순서: 요청 → 결론 → 결정표 → 비교 → 위험 → 열린 질문 → 코드 읽기 지도
- 길이감: 300~1500 어절 (상한 초과 → 질문별로 문서를 나눈다, 하한 미만 → 선택지·버린 이유·위험이 빠졌는지 본다)
- 자세함: 선택지마다 비용, 적용 시점, 위험을 같은 기준으로 쓴다. 추천 이유와 버린 선택지의 장점까지 쓴다. 승인에 쓰이지 않는 구현 세부(클래스 이름, 단계별 명령)는 쓰지 않는다.
- 가독성 장치: 맨 위 요약(요청과 추천을 세 줄 안에), 섹션별 한 줄 결론, 계산 과정은 접기.
- 요소:
  - 각주: 선택 — 수치의 근거 출처를 달 때만. 결정자는 근거를 확인하고 싶지만 본문은 결정에 집중해야 한다.
  - 표: 쓴다 — 선택지 비교는 표가 가장 빨리 읽힌다.
  - 그림: 선택 — 선택지가 구조를 바꿀 때 전후 그림 하나. 구조가 그대로면 그리지 않는다.
  - 콜아웃: 쓴다 — "결정 필요" 하나를 맨 위에. 그 이상은 쓰지 않는다.
  - 접기: 선택 — 계산 과정, 조사 상세. 결정에 직접 쓰이는 수치는 접지 않는다.
  - 용어표: 쓰지 않는다 — 결정자는 대개 도메인을 안다. 낯선 말은 문장 안에서 푼다.
  - 코드 지도: 선택 — 리뷰어가 지금 코드를 열어 볼 때만.
- 이 유형에 넣지 않는 것: 조사 순서대로 쓴 일지, 승인 뒤의 구현 계획 세부(따로 쓴다), 대안 없는 설계.

## 쓰는 법

- 결정할 질문마다 결정표 네 칸(왜 나왔나 · 이번 범위인가 · 선택지 · 추천과 이유)을 채운다. 칸이 비면 결정할 준비가 안 된 것이다.
- 질문에는 마감을 붙인다. "언제까지 누가 고르는지"가 요청 블록에 있어야 한다.
- 추천이 있어도 선택지를 공정하게 쓴다. 버린 쪽의 장점, 고른 쪽의 위험을 숨기지 않는다.
- 아직 계산하지 않은 값은 추정치로 채우지 않는다. 열린 질문에 "누가 언제 계산하나"로 남긴다. 추정이 꼭 필요하면 계산식과 함께 `[추정]`을 붙인다.
