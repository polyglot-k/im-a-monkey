# PR 설명 (pr)

- 언제: 리뷰어가 diff 옆에 띄워 두고 읽으며 승인할지 정한다. 머지한 뒤에는 "이 변경이 왜 들어갔지?"를 찾는 기록이 된다.
- 블록 순서: 결론 → 변경 전후 → 절차(검증) → 위험 → 요청
- 길이감: 80~600 어절 (상한 초과 → PR을 나누거나 설계 설명은 문서로 옮기고 링크한다, 하한 미만 → 왜 바꿨는지·어떻게 확인했는지·되돌리는 법이 빠졌는지 보고, 원문에 없으면 묻거나 `<채울 값>`으로 남긴다)
- 자세함: 무엇을 왜 바꿨는지 한두 문장. 변경은 리뷰어가 diff를 읽는 단위(파일이 아니라 의미 묶음)로 나눈다. 검증은 돌린 명령과 결과를 그대로 쓰고 못 한 확인은 못 했다고 쓴다. 위험에는 누가 영향받는지와 되돌리는 법을 쓴다.
- 가독성 장치: 맨 위 1~2문장 요약. 소제목으로 칸을 나눈다(요약 · 변경 · 검증 · 위험과 되돌리기 · 리뷰 포인트). 검증은 체크리스트로 쓴다. 섹션별 한 줄 결론은 쓰지 않는다(칸 이름이 이미 결론이다).
- 요소:
  - 각주: 쓰지 않는다 — PR 화면은 위에서 아래로 한 번 훑고 끝난다. 근거는 링크로 그 자리에 둔다.
  - 표: 선택 — 변경 묶음이 셋 이상이거나 전후 값을 비교할 때.
  - 그림: 선택 — 화면이 바뀌면 전후 캡처, 흐름이 바뀌면 흐름도 하나.
  - 콜아웃: 선택 — 머지 전에 꼭 해야 할 일(마이그레이션, 설정 변경)이 있을 때 "주의" 하나.
  - 접기: 선택 — 긴 테스트 로그나 출력. 결과 한 줄은 접지 않는다.
  - 용어표: 쓰지 않는다 — 리뷰어는 같은 팀이다. 낯선 말은 그 문장에서 푼다.
  - 코드 지도: 선택 — diff가 크면 "이 순서로 보세요"를 리뷰 포인트에 쓴다. 파일 목록을 옮겨 적지는 않는다(diff에 있다).
- 이 유형에 넣지 않는 것: 커밋 목록 복사, 파일 목록 복사, 설계 논의 전체(결정 요청이나 ADR로 나누고 링크한다), 장식용 볼드와 이모지.

## 쓰는 법

- 제목은 무엇이 바뀌는지 한 줄로 쓴다. 저장소에 커밋 접두어 규칙이 있으면 따른다.
- 검증 체크리스트는 실제로 한 것만 체크한다. 안 한 확인은 빈칸으로 두고 이유를 한 줄 붙인다.
- 리뷰 포인트에는 리뷰어가 특히 봐 줬으면 하는 곳과 이유를 쓴다. "전부 봐 주세요"는 쓰지 않는다.
- 메신저로 PR 링크를 보낼 때는 이 유형이 아니라 message 유형으로 요청 한 줄과 링크만 쓴다.
