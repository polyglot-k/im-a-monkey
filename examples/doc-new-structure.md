# monkey-doc 예시: 기본 유형에 맞지 않는 요청

## 전

요청: "새로 온 팀원이 개발 환경을 직접 따라 세팅하면서, 왜 이렇게 구성했는지도 같이 이해하는 가이드를 써 줘. 설정은 `.env` 파일에 값을 넣고 `make setup`을 돌리는 거고, 값은 팀 비밀 저장소에서 받아."

의도: 새 팀원 · 따라 하면서 이해하기 · 하루 안에 · 위키 · 오래 씀

따라 하기(howto)와 이유 설명(explain)이 반씩 걸려요. 둘로 나누면 따라 하는 사람이 단계 중간에 이유를 찾으러 다른 문서로 가야 해요. 그래서 새 구조를 조립했어요.

## 새 구조

```
# 따라 하며 이해하기 (guided-setup)
- 언제: 새 팀원이 단계를 따라 하면서, 각 선택이 왜 그런지도 읽고 이해한다.
- 블록 순서: 결론 → 절차 → 점검 질문 → 위험
- 길이감: 200~800 어절
- 자세함: 단계마다 명령과 끝났을 때의 모습을 쓴다. 이유는 독자가 "왜?"하고 멈출 곳에만 두세 문장으로 쓴다. 이유가 길어지면 따로 동작 설명 문서로 링크한다.
- 가독성 장치: 맨 위에 전제와 끝난 기준, 번호 단계, 단계마다 이유를 접는 상세로
- 요소:
  - 각주: 쓰지 않는다 — 따라 하는 중에 시선이 아래로 튀면 단계를 놓친다
  - 표: 쓰지 않는다 — 단계 사이의 표는 흐름을 끊는다
  - 그림: 선택 — 구성 요소가 여럿이라 전체 모습이 필요할 때 맨 앞에 하나
  - 콜아웃: 쓴다 — 되돌릴 수 없는 단계 바로 앞에 "주의"
  - 접기: 쓴다 — 이유를 접어 두면 따라 하는 사람은 흐름을 지키고 궁금한 사람만 펼친다
  - 용어표: 쓰지 않는다 — 낯선 말은 그 단계에서 푼다
  - 코드 지도: 선택 — 설정이 코드의 어느 곳을 읽는지 궁금한 사람을 위해 맨 아래에만
- 이 유형에 넣지 않는 것: 설계 결정 비교, 사고 경과, 단계마다 붙는 긴 이유
```

## 후

# 개발 환경 세팅

`.env` 파일에 값을 채우고 `make setup`을 돌리면 개발 환경이 만들어져요. 끝난 기준은 `make setup`이 오류 없이 끝나는 거예요.

- 전제: 팀 비밀 저장소에서 값을 받을 권한이 있어요.
- 걸리는 시간: `<채울 값>`

## 절차

1. 팀 비밀 저장소에서 개발용 값을 받아 `.env` 파일에 넣어요.

   <details><summary>왜 `.env` 파일인가요?</summary>
   값을 코드와 따로 두면 저장소에 비밀이 올라가지 않아요. `<채울 값>`
   </details>

2. 설정 명령을 돌려요.

   ```
   make setup
   ```

   기대 출력: `<채울 값>`

## 점검 질문

- 값을 받은 곳이 어디인가요? 팀 비밀 저장소가 맞나요?
- `make setup`이 어떤 파일을 읽는지 설명할 수 있나요?

## 위험

- `.env`를 저장소에 올리면 안 돼요. 올렸을 때 대처는 `<채울 값>`이에요.
- `make setup`이 실패하면 어느 단계에서 어떤 메시지가 나왔는지 `<채울 값>`에 붙여서 물어보세요.
